# Security model and limitations

This document says plainly what ccvet does and does not protect against, so nobody over-trusts it.

## What ccvet is

ccvet is a heuristic and optional-LLM advisory gate for Claude Code's `PreToolUse` hook. It classifies each tool call before it runs and returns one of four decisions: allow it automatically, block it outright, ask you, or defer to Claude Code's normal permission flow. The goal is to reduce how often an obviously destructive command slips through approval on autopilot, and to cut down on the prompt fatigue that makes people stop reading permission prompts in the first place.

## What ccvet is not

- **Not a sandbox.** ccvet classifies the command text before it runs. It does not isolate, contain, or limit what an approved command can actually do on your system.
- **Not a substitute for least privilege.** If you run Claude Code with broad filesystem or network access, ccvet reduces risk but does not eliminate it. Running Claude Code in a container or on a disposable machine for anything you don't fully trust is still the stronger control.
- **Not a complete static analyzer.** The rule engine (Layers 0 and 1) and the obfuscation heuristics catch known-dangerous patterns and known evasion shapes. They do not exhaustively enumerate every way a command could be dangerous, and a sufficiently novel or convoluted command may reach the gray zone (an "ask", or an LLM opinion) instead of being correctly identified as dangerous outright.
- **The optional LLM classifier (Layer 2) cannot block anything.** This is by design, not an oversight. Layer 2 can only promote a gray-zone command toward "allow". It can never produce a "deny". This means a misconfigured or hallucinating local model can accidentally approve something it should not, but it can never be tricked into unilaterally blocking your agent's legitimate work. Denial authority stays exclusively with the hard-coded guards in Layer 0, which no configuration, user policy, or model opinion can override.

## Threat model

ccvet assumes:

- The person running it trusts the Claude Code agent's general intent, and wants a safety net against a wrong turn (a destructive command generated or run by mistake), not protection against a Claude Code session that has itself been fully compromised by an attacker with arbitrary code execution.
- The command text passed to the hook is the actual command about to run. ccvet does not execute anything itself; it only reads and classifies the text Claude Code hands it.
- A local LLM used for Layer 2 may be unreliable, slow, or occasionally wrong, and the design accounts for all three (timeouts fail safe, malformed output fails safe, and incorrect-but-well-formed output can only ever loosen a decision toward "allow", never block one).

ccvet does **not** defend against:

- A fully compromised or adversarially controlled Claude Code process that bypasses the hook mechanism entirely (for example, by disabling hooks or by running commands through a path ccvet never sees).
- Prompt injection that convinces the agent to generate a dangerous command in the first place. ccvet classifies the command once it exists; it does not prevent the agent from deciding to write one. (Its own Layer 2 prompt is hardened against the specific case of injected text trying to talk the *classifier* into approving itself: the command is passed as a JSON-encoded string rather than interpolated into a markdown fence, so a command containing literal triple-backticks can't structurally break out of the "this is data" framing. That's a narrower claim than defending against injection in general.)
- Any risk introduced by a command ccvet classifies correctly as safe, but which is genuinely safe only in some other context ccvet cannot see (for example, a command that is safe on your laptop but destructive against a shared production system you happen to be connected to).

## Known gaps

- **`case`, `select`, `coproc`, `[[ ... ]]` test expressions, and arithmetic `for ((...))` loops in Bash are not parseable by the underlying shell parser (`bashlex`).** They fall back to `ask` rather than being actively classified. This is a library limitation, not a ccvet bug, and it fails toward asking, not toward silently allowing.
- **ANSI-C quoting (`$'...'`) around a flag argument can downgrade a hard-coded guard's result from `deny` to `ask`.** `rm $'-rf' /` is one example: bashlex mis-parses the quoted flag rather than dequoting it, so the catastrophic-rm check doesn't recognize it as `-rf`. This still fails toward asking you, never toward silently allowing the command. Ordinary single and double quotes are unaffected.
- **Windows and PowerShell are out of scope for v1.** The rule engine targets POSIX shells (bash and zsh on macOS and Linux). This is a deliberate, stated scope decision, not an unnoticed gap.
- **The rule engine covers Bash, file read/write tools, and a few other built-in Claude Code tools.** Third-party or future MCP tools ccvet has no rule for are deferred to Claude Code's own normal permission flow rather than auto-approved, but they are not actively classified by ccvet either.
- **`.gitconfig` is not treated as a credential path, unlike `.git-credentials`, `.npmrc`, and the other dedicated credential stores.** This is a deliberate, considered call, not an oversight: `.gitconfig` is an ordinary config file (`user.name`, `[alias]` entries, `core.*` settings) that only atypically embeds a credential, e.g. a rewritten remote URL under `[url "..."]`. Treating it as a hard deny would repeat the mistake the original `.env` pattern made before the `.env.example` carve-out, just in the other direction. If you deliberately route credentials through `.gitconfig` (uncommon, but possible), be aware ccvet won't flag reads or writes to it the way it flags `.git-credentials`.
- **A `ccvet allow` promotion's whole-command anchoring (added in v0.0.9) is not retroactive.** A rule already sitting in `policy.yaml` from before that release, or written directly via `userpolicy.add_rule()` rather than the CLI, stays exactly as unanchored, and exactly as over-broad, as it always was; upgrading ccvet does nothing to existing rules. `ccvet status` now warns about any loaded rule whose pattern doesn't start with `^` and end with `$`, but it's read-only - it won't rewrite a stored rule for you, since a stored pattern string carries no record of whether it was meant as an exact literal (should be anchored) or a deliberately broad `--regex` pattern (shouldn't be). If `ccvet status` flags a rule you wrote before v0.0.9 as a literal promotion, re-run `ccvet allow` on it to get the exact-match version.
- **The audit log's secret redaction (`redact.py`, added after four review rounds flagged the plaintext-secret-sink issue) is best-effort, not exhaustive.** It catches Authorization headers, URL-embedded credentials, well-known provider token prefixes (OpenAI, GitHub, AWS, Google, Slack, JWTs), and inline `VARNAME=value` assignments where the name itself announces what it is. A secret with no structural signature at all (a bare, unlabeled random string with no recognizable prefix, passed as a plain positional argument) will not be caught, and `~/.ccvet/audit.jsonl` should still be treated as potentially sensitive, not as safe to share. The redaction is deliberately over-inclusive where that's ambiguous (a non-secret variable name that happens to end in `KEY` or `PASS`, e.g. `MONKEY=banana`, also gets redacted) - the asymmetry favors losing a little log detail over missing a real secret.

Fixed during hardening and worth naming, since they illustrate the kind of bug this project watches for:

- Compound shell constructs (`{ ...; }`, `(...)`, `if`/`while`/`for`), process substitution (`<(...)`/`>(...)`), and the transparent wrappers `eval`/`exec`/`command`/`builtin` all used to let their wrapped command dodge classification entirely and fall through to `allow`.
- **Shell redirections were completely invisible to classification.** A redirect target (the right-hand side of `>`, `>>`, `<`, `<<<`) never appears in a command's argument list, so `curl ... < ~/.aws/credentials` (exfiltrating a credential file via input redirection) or `echo ... >> ~/.bashrc` (a persistence write) had no sensitive path visible anywhere. Redirect targets are now extracted and checked the same way Edit/Write tool paths are.
- Secret/persistence/manifest path matching used a raw substring search on the full resolved path, so `/etc/passwd` matched `/etc/passwd_notes.md`, `.bashrc` matched `my.bashrc_backup.txt`, and so on. Since the credential-path match is a hard, non-overridable deny, a false positive there couldn't even be worked around. Matching is now component-aware against the path's actual segments.
- The catastrophic-target list for `rm -rf`/`chmod -R` was missing several top-level system directories (`/var`, `/opt`, `/Applications`, `/Library`, `/root`, and others), didn't recognize a literal home-directory root (`/Users/<name>`, `/home/<name>`) as catastrophic, didn't catch a bare `*` wildcard, and (for chmod) only recognized octal `777`/`000`, not symbolic-mode grants like `a+rwx` that achieve the same thing.
- The DELETE/UPDATE-without-WHERE check scanned the whole command's text rather than the specific SQL statement, so a genuinely unconditional `DELETE FROM users` paired with an unrelated `WHERE` elsewhere in the same multi-statement command escaped detection.

Found by an external static review of the published package, after the above (which were all found internally):

- **`cat $(ls -d ~/.ssh)/id_rsa` fully bypassed to `allow`.** The secret-path guard's substring check couldn't see `.ssh/id_` in the raw argument text (the closing paren breaks the match), and since `ls` is independently extracted and classified on its own, `cat` being on the allowlist let the whole thing through with no awareness that its argument's real value was unverifiable. Fixed: an auto-approved verdict is now downgraded to `ask` whenever an argument (not just the command name) contains a substitution or variable expansion that isn't a self-contained, independently-classified one (see `Docs/risk-taxonomy.md` for the exact distinction, including why `<(ls -la)` alone is unaffected).
- **`env` with no arguments was on the auto-approve allowlist.** It prints every environment variable, which for an agent session commonly includes active API keys and tokens. The project's own taxonomy document already said this should ask, not auto; the shipped policy file simply disagreed with its own documentation, and nothing had ever tested it specifically. Fixed.
- **`git remote` and `git tag` were treated as blanket read-only, with no check on their mutating sub-forms.** `git remote add`/`remove`/`set-url` (which can silently redirect future pushes to an attacker-controlled remote) and `git tag -d`/`--delete` were all auto-approved. Fixed with the same flag-sensitive handling `push`/`reset`/`clean`/`branch` already had.
- **`.env`, `.netrc`, `.npmrc`, `.pypirc`, and `.envrc` were entirely absent from the credential-path list.** `.env` in particular is arguably the single most common real-world location for secrets in an actual project. Fixed for both Bash commands and Edit/Write/Read tool calls.

A second round of external review, after the v0.0.2 release, found three more:

- **A substitution inside a redirect target was a second instance of the same bypass class.** `cat myfile > $(echo ~/.bashrc)` extracted the redirect target as the raw, unexpanded text `$(echo ~/.bashrc)`, which doesn't match any literal pattern, and nothing checked whether a redirect target was dynamically constructed the way an argument now is. Fixed (at the time) by denying any redirect target containing a substitution or variable expansion outright, with no override, since there's no independent way to verify a *destination* path the way classifying an inner command can verify a *data source* like `<(ls -la)`. A third round of review (below) revisited this specific choice.
- **The `.env` credential-path check for Bash arguments was a raw substring match, not component-aware like the Edit/Write path check already was.** `cat .env.example`/`.env.local`/`.env.sample` (common, safe conventions for documenting required variables, not real secrets) were denied. Fixed by reusing the same component-aware matcher for both.
- **`git remote prune` was missing from the mutating-subcommand list**, alongside `add`/`remove`/`set-url`/etc. Fixed.

A third round of external review, after the v0.0.4 release, found three more, plus one architectural bug found while verifying them:

- **Claude Code's own config files were not treated as persistence vectors.** `.claude/settings.json`, `.claude/settings.local.json`, `~/.claude/settings.json`, `.mcp.json`, `.claude/commands/`, and `.claude/agents/` (the files that define Claude Code's own permissions, hooks, and MCP servers) were entirely absent from the persistence-path list, so `cat evil > .claude/settings.json` classified as a plain `allow` via Bash, even though the identical file via Edit/Write already asked (project-local) or denied (outside the project root). A rewritten settings file can silently drop ccvet's own hook in the next session, making this exactly the "agent quietly makes itself persistent" class the rest of the list exists to stop. Fixed by adding these to `PERSISTENCE_PATTERNS`, closing the Bash-vs-Edit asymmetry.
- **`.env.local`, `.env.production`, and other `.env.*` variants were unmatched.** The component-exact fix from the second round correctly stopped denying `.env.example`/`.env.sample`, but went one step too far in the other direction: only the bare `.env` component matched exactly, so `.env.local` (the conventional home of real secrets, e.g. Next.js's env-file loading order) read straight through as `allow`. Fixed with a dedicated prefix-plus-safe-suffix check (`.env` or `.env.*`, except a short list of known documentation suffixes: `.example`, `.sample`, `.template`, `.dist`, `.defaults`), shared by the Bash and Edit/Write/Read paths.
- **Dynamic redirect targets were a hard, non-overridable deny with no escape hatch for a perfectly ordinary idiom.** The second round's fix (above) was correct in direction but too blunt: `cat x > $(mktemp)` is common and nearly always benign, yet had no `ccvet allow` path, unlike a dynamic *argument* (`classify_argv`'s equivalent case), which asks and stays overridable. Revisited the choice explicitly: a *pure*, self-contained substitution with nothing concatenated around it (`$(mktemp)`, and also `$(echo ~/.bashrc)` even though its inner command's own argument looks sensitive, since there's no independent way to verify what a redirect *destination* resolves to) now downgrades to an overridable `ask` instead of a hard `deny`. Anything less clean, literal text concatenated around a substitution or a bare variable expansion, stays a hard, non-overridable `deny`, matching the "can't verify the command name, deny" precedent used for dynamically-constructed command names.
- **Found while verifying the above, not named by the reviewer: `overridable=True` on a `secret_path_guard`- or `redirect_target_guard`-sourced verdict had never actually worked.** `shellrules.evaluate()` returned straight from either guard before the override-check block (project/global policy file, then Layer 2) was ever reached; that block only ran for verdicts produced by `classify_argv`. A `ccvet allow` for, say, the generic token/secret/credential-name heuristic genuinely had no effect, and no test had ever exercised it end to end. Fixed by collecting every guard's verdict into one list, taking the most severe, and running the override pipeline exactly once regardless of which guard produced the winner. This was a prerequisite for the `$(mktemp)` escape hatch above to actually work, not just a cosmetic change.

Two further observations after the above landed, both about the fixes themselves rather than new bypasses, and both addressed:

- **A bare variable redirect target (`cmd > $OUT`) was still a hard, non-overridable deny.** `OUT=report.txt; cmd > $OUT` is an entirely ordinary shell idiom, no different in risk from the `$(mktemp)` case that was just downgraded to an overridable `ask`, but the fix above only broadened the pure-substitution check, not bare variables. Fixed: the same "is the whole target purely one dynamic token, nothing concatenated" check (using bashlex's position spans) now applies uniformly to a bare variable too, so `$OUT` asks like `$(mktemp)` does, while `${OUT}.bak`-style concatenation still denies.
- **Fixing the inert-overridable-flag bug (above) silently widened Layer 2's reach.** `classifier.classify()` has no opinion on the input decision, it's purely gated by whether `shellrules.evaluate()` calls it at all, so once guard-level overridable verdicts started reaching the override block, a one-shot, unreviewed local-model opinion could promote an overridable *deny* (the generic token/secret/credential-name heuristic) to `allow`, not just an overridable *ask*. That contradicts `classifier.py`'s own documented contract ("can only turn an ask into an allow, never a deny"), which held before only as an accident of the bug it was fixed alongside. Decision: keep Layer 2 restricted to the `ask` tier only; a human-reviewed `ccvet allow` policy rule is a different trust tier and keeps working on any overridable verdict, deny included.

All of the above are fixed and covered by regression tests now. If you find a case like this, see "Reporting a vulnerability" below.

## Operational wiring review: `ccvet init`/`uninstall`, not the classifier

A different kind of review, a sandboxed round-trip test of the actual `init`/`status`/`uninstall` commands against real `settings.json` files rather than a static read of the classification code, found one real bug and one real (if minor) accuracy gap:

- **A bare `"ccvet gate"` hook command silently never runs when the venv it's installed into isn't on the PATH of the shell Claude Code spawns the hook in.** Confirmed directly: with `PATH` stripped to a bare system shell (simulating that spawn), `sh -c "ccvet gate"` fails with `command not found` (exit 127), and per the documented PreToolUse failure behavior above, that failure is swallowed and falls through to the normal permission flow, no error shown anywhere. `ccvet status` still reports the hook as wired; only an empty `~/.ccvet/audit.jsonl` reveals it never actually ran. A venv install (the common case, and what `pip install ccvet` inside a project venv looks like) is exactly the shape where the interactive shell `ccvet init` was run from and the shell Claude Code later spawns the hook in don't have to share a PATH. Fixed: `ccvet init` now resolves and writes the running interpreter's absolute path (`sys.executable`'s sibling `ccvet`, which pip/pipx/hatchling always install alongside it), not the bare name, confirmed fixed with the same PATH-stripped reproduction. `ccvet uninstall`/`status`'s matching logic was updated to recognize an entry by shape (ends in `ccvet gate`, whatever the prefix) rather than exact string equality, so a stale absolute path from a prior install is cleanly replaced on re-`init`, not left duplicated alongside a new entry.
- **The write-confirmation preview didn't always show the exact bytes that landed on disk.** The preview printed `json.dumps(..., sort_keys=True)`; the actual `path.write_text(...)` call used plain `json.dumps(...)` with no `sort_keys`. On a `settings.json` with existing unsorted keys, what the user approved at the `Write this? [y/N]` prompt and what actually got written were two different byte sequences, JSON-semantically equivalent, but not the same text. Fixed by writing the exact string already computed for the preview, rather than re-serializing separately; the two can no longer diverge by construction.
- **Not a bug, confirmed as an accepted, permanent tradeoff rather than a stale "later phase will fix this" placeholder**: `ccvet init`/`uninstall` re-serialize the whole `settings.json` file rather than doing a surgical, format-preserving patch, so a 4-space-indented file becomes 2-space, and `uninstall` doesn't restore the original formatting either. This project's own module docstring used to point at a future phase ("Phase 2 needs a less invasive merge") that shipped without actually addressing it; the docstring is corrected to state plainly that this is accepted as-is (a format-preserving JSON patcher is real engineering effort for a payoff that's only `git diff` noise on a file nobody hand-edits often), not a forgotten TODO.

Fixed and covered by regression tests, including a real end-to-end reproduction (a stripped-`PATH` subshell actually failing to resolve the bare command, then actually resolving the absolute-path one) alongside the unit tests.

Two further nits on those fixes, both closed rather than left as caveats:

- **The absolute-path resolution's own fallback was silent.** When no `ccvet` binary sits next to the running interpreter (the rare case of `python -m ccvet.cli init` from a source checkout with no installed console script), `_hook_binary()` quietly wrote the bare `"ccvet"` name again, the exact shape the fix above exists to avoid, just on a rarer path, with nothing telling the user it happened. Fixed: that branch now prints a warning pointing at `ccvet status` and `~/.ccvet/audit.jsonl` as the way to confirm the hook is actually firing.
- **The shape match required exactly two tokens.** `_is_ccvet_entry` recognized `"<path>/ccvet gate"` but not a hand-edited `"<path>/ccvet gate --dry-run"` (or any future flag ccvet itself gains after `gate`), so a legitimately-edited entry would read as an unrelated hook to a later `uninstall`/re-`init`/`status`, left duplicated or orphaned. Fixed by matching "at least two tokens, second is `gate`" instead of "exactly two", a strict widening that can't un-match anything previously matched.

## Adversarial and robustness testing round: five findings, none an architectural bypass

A broader pass (a 29-case adversarial corpus, 11 malformed-input cases, 16-way concurrent audit-log writes, and a fake OpenAI-compatible server exercising the real Layer 2 contract) confirmed no architectural bypass: the adversarial corpus landed entirely on deny/ask, malformed input always produced valid JSON and never crashed, concurrent audit writes never corrupted, the safety floor survived an explicit `ccvet allow` rule written directly into policy.yaml for it, and Layer 2's documented contract (promote only when low-risk/reversible/local-or-repo, never touch a non-overridable verdict, fail to `ask` on a timeout or malformed response) held exactly as designed. Five real coverage gaps and footguns did turn up, all fixed:

- **Several other credential stores besides `.ssh`/`.aws`/`.env` were auto-approved.** `.git-credentials` (git's own credential helper writes plaintext `user:token@host` lines here), `.config/gh/hosts.yml` (the GitHub CLI's OAuth token), `.docker/config.json` (base64-encoded registry auth, the same risk tier as the already-covered `.npmrc`/`.pypirc`), and `.aws/sso/cache/*` (cached AWS SSO bearer tokens) all read straight through as `allow` via both `cat` and the `Read` tool, the same class of gap `.env` itself was in before the first external review round. Fixed by adding all four to the secret-path lists (shared by Bash and Edit/Write/Read, as always). Deliberately **not** added: `.gitconfig`. Unlike the four above, which are exclusively credential stores by design, `.gitconfig` is an ordinary config file that only atypically embeds a credential (e.g. a rewritten remote URL) - the same `.env`-vs-`.env.example` judgment call, just for a whole file instead of a filename suffix.
- **`ccvet allow` patterns were unanchored substring regexes, even in "literal" mode.** `--regex` was never the issue; a plain `ccvet allow "ls"` stored the escaped-but-unanchored regex `ls`, which `re.search` happily matched inside `ls -la`, `lsof -i`, and `false-ls-check` alike - a promotion the user believes is narrow ("allow exactly the command I just reviewed") was silently widening the allow surface to "allow anything containing this text", with no indication it had done so. Separately, typing the anchors by hand (`ccvet allow "^npm test$"`) made things worse, not better: without `--regex`, the whole string gets `re.escape`d, including the `^`/`$` themselves, so the stored pattern became a literal search for the four characters `^`, `$` and backslashes, which never matches the real `npm test` text at all. **This is the one worth fixing first**, per the review that found it, and the one most likely to erode trust silently. Fixed: the non-`--regex` path now wraps the escaped pattern in `^...$`, an exact whole-command match, matching what "literal string" actually implies to someone typing it; `--regex` is unaffected and stays an explicit, documented opt-in for anything broader (the module's own docstring example, a deliberately unanchored-at-the-end prefix match, relies on this).
- **Grep/Glob's `pattern` field (what to search for) was being resolved and checked as if it were a filesystem path (where to look).** `Grep(pattern=".env.production")`, an entirely ordinary search for that literal text, denied outright with "touches a credential path" even though no actual path was involved; `Glob(pattern="**/.ssh/id_*")` denied the same way. Worse, passing a benign `path` alongside the pattern made it `allow` instead, since `path` was checked first and `pattern` was never looked at once that short-circuited - an inconsistency that made the bug harder to notice, not easier. Fixed by dropping `pattern` from the set of fields ever treated as a path; Grep/Glob's real scoping field is `path`, same as every other tool. A bare `Grep(pattern=...)` with no `path` at all (search the whole project, an entirely ordinary case) now correctly allows instead of asking, matching the "Read-only tools are AUTO by construction" design this project has stated since the original taxonomy.
- **The `chmod` home-directory-root fix from an earlier round was only half-wired.** `rm -rf /Users/charan` denies (a literal home-directory-root heuristic, since the exact path can't be known in advance the way `/etc` can), but `chmod -R 777 /Users/charan` only asked, despite a prior round's note claiming this case was covered - `chmod`'s own catastrophic-target check never actually called the heuristic function `rm`'s does, just a plain fixed-set membership test. Fixed by sharing the same underlying check (parameterized by each command's own target set, so `chmod` doesn't also inherit `rm`'s bare-wildcard entries like `*`, which aren't meaningful for a permission change).
- **The audit log is a permanent, unredacted plaintext secret sink, confirmed, not just theorized.** A bearer token passed on a command line (`-H 'Authorization: Bearer sk-...'`) was written verbatim into `~/.ccvet/audit.jsonl`. This is the already-documented tradeoff (file permissions `0600`, local-only), not a new bug, but confirmed real rather than assumed: there is no redaction, truncation, or rotation, and every inline token or secret that ever appears in a Bash command's argv accumulates there forever. The same caution extends to Layer 2 if `classifier.base_url` is ever pointed at a remote endpoint rather than a local model server.

Two items noted as correctly-understood, non-actionable "for your information", not bugs: a null `tool_input` on a `Bash` call degrades to an empty command, which allows (nothing runs, so there's nothing to classify) rather than crashing; and `Read` allows any path outside the project root or matching a persistence pattern, since reading a file has no side effect by itself (unlike `Edit`/`Write`, which are project-bound) - both exactly as designed, not gaps.

22 new regression tests across `test_bash_rules.py`, `test_fs_rules.py`, and `test_commands.py` (380 total, up from 358). If you find a case like this, see "Reporting a vulnerability" below.

## Round-two verification of v0.0.9 (2026-11-27): one caveat, one documentation gap

An independent re-check of v0.0.9 (checksum-verified against the actual PyPI upload) confirmed all five findings above as fixed, with no new bypass surface opened by any of the fixes. Two follow-ups:

- **The `^...$` anchoring fix is not retroactive, and that's now in "Known gaps" above, not only in a code comment.** A rule written before v0.0.9, or written directly via `userpolicy.add_rule()` rather than the CLI, stays exactly as unanchored as it always was - upgrading ccvet changes nothing about rules already on disk. Confirmed directly: seeding a project policy.yaml with an unanchored `match: ls` rule and re-running `lsof -i` against it still returned `allow`. Chose a read-only `ccvet status` warning over auto-migration: a stored pattern string carries no record of whether it was meant as an exact literal (should be anchored) or a deliberately broad `--regex` pattern (shouldn't be), so silently rewriting it on upgrade risks narrowing a rule someone wrote on purpose, which is a worse failure mode than leaving it alone and telling the user. `ccvet status` now lists any loaded rule whose pattern doesn't both start with `^` and end with `$`, with a pointer to re-run `ccvet allow` on it if it was meant as a literal promotion.
- **`.gitconfig` not being treated as a credential path is a deliberate, considered call** (see "Known gaps" above), correctly identified by review as defensible but as something that belongs in the documented gaps list rather than only in `paths.py`'s own comment, since it's a conscious residual someone relying on this project should be able to find without reading the source.

1 new regression test in `test_commands.py` for the `ccvet status` warning, plus the pre-existing "does not warn about an anchored rule" negative case. 382 tests passing (up from 380).

## Verification of v0.0.10 (2026-11-27): a crash in the new warning itself, and a wording nit

A checksum-verified re-check of v0.0.10 confirmed it changed only `status()` (classification and `ccvet allow` behavior byte-identical to the already-verified v0.0.9), and that the new unanchored-rule warning behaves as documented. It also found a real crash in that same new code, ironic given what it's for:

- **`ccvet status` crashed on a hand-edited `policy.yaml` with a non-mapping rule item** (`rules:\n  - just a string\n`), with an `AttributeError` from calling `.get("match")` on a plain string. Confirmed directly, and confirmed the gate path was never affected: `userpolicy.find_override()` already guards exactly this case (`if not isinstance(rule, dict): continue`), specifically so a malformed policy file can't take anything down - the new `status()` loop was the one place that check hadn't been carried over to. Fixed by mirroring the same guard. Severity note: this was never a protection gap (the hard-coded floor and the override pipeline were both unaffected the whole time), just a crash in a diagnostic command on an ordinary YAML mistake (a misplaced dash, a half-finished edit).
- **The warning's wording overstated reach for a partially-anchored rule.** A pattern like `^docker build\.` (this project's own docstring example) is anchored at the start, so it's a prefix match, not an "substring search anywhere in the command text" the way a fully unanchored pattern is. Flagging it at all is still reasonable (a prefix match covers more than one exact command), but the description was inaccurate. Fixed: each flagged rule now gets its own accurate description (prefix search, suffix search, or substring search anywhere), rather than one blanket claim for all three shapes.

4 new regression tests in `test_commands.py` (the crash reproduction, the prefix-wording case, the suffix-wording case, and an empty-`match`-key edge case for full coverage). 386 tests passing (up from 382), 100% coverage on `commands.py` maintained.

## Verification of v0.1.0: the real bug behind the status crash, found one level down

A checksum-verified re-check of v0.1.0 confirmed the status crash and wording fixes above, then found that the `isinstance(rule, dict)` guard stopped one level too early - and that the deeper version of the same gap was far more serious than a diagnostic-command crash:

- **A non-string `match` value (`match: 5`, `match: true`, `match: [a, b]`) still crashed `ccvet status`**, since the guard added for v0.0.10 checked the rule item's type, not the `match` value's type, and `match = rule.get("match") or ""` only filters a *falsy* value, not a truthy non-string one. That alone would have been another instance of the same class of crash. What made it the more severe finding: `userpolicy.find_override()` has the exact same gap, and `find_override()` isn't a diagnostic command, it's called from `shellrules.evaluate()` on **every single overridable verdict**, which includes every plain `AUTO_PROGRAMS` auto-allow (`ls`, `cat`, `grep`, `git status`, ...), not just the hard-coded safety-floor guards. Confirmed directly: a single `match: 5` rule anywhere in `policy.yaml` raised an uncaught `TypeError` from `re.search(5, command)` inside `find_override()`, which `gate.py`'s blanket exception handler silently turned into `ask` for every overridable command project-wide, with a generic "internal error" reason giving no hint that a malformed policy rule was the cause. **This was the first real instance, across ten review rounds, of a bug that could degrade ccvet's actual day-to-day value (fewer prompts) rather than only widen or narrow a specific classification.** Fixed in both places: `find_override()` and `status()`'s own loop now both require `isinstance(pattern, str)` before doing anything with it, skipping (not crashing on) anything else, the same tolerance `_load_file`'s non-dict-rule handling already had.
- **Added, per the review's own suggestion**: `ccvet status` now counts and reports rules it couldn't evaluate (missing, empty, or non-string `match`) as an explicit "N rule(s) could not be evaluated" note, rather than silently skipping them with no visible trace. This is specifically the diagnostic gap behind the finding above: if a bad rule is ever silently degrading a project's prompts again, `ccvet status` now says so directly instead of either crashing or saying nothing.

9 new regression tests across `test_userpolicy.py` and `test_commands.py` (395 total, up from 386), 100% coverage on `commands.py` and `userpolicy.py` maintained. Re-verified end to end through the real hook path (`ccvet gate` with a seeded `match: 5` rule): `ls -la` now allows correctly instead of degrading to a generic `ask`.

## Audit-log secret redaction (2026-11-27): the one item left open across four review rounds

The plaintext-audit-log finding (first confirmed real, not theorized, in the "Adversarial and robustness testing round" above) had been flagged four times with the same conclusion each time: a documented tradeoff, not a bug, no code change. After the fourth flag, decided it was worth actually closing rather than deferring again:

- **Added `redact.py`**: best-effort pattern-based redaction applied to a Bash command's text and a `WebFetch` URL before either is written to `~/.ccvet/audit.jsonl` (Write/Edit content was already hashed, not stored, from Phase 2 onward - this closes the one input type that wasn't). Catches Authorization headers (`Bearer`/`Basic`), credentials embedded in a URL (`https://user:pass@host`), well-known provider token prefixes (OpenAI `sk-`, GitHub `gh[pousr]_`, AWS `AKIA`, Google `AIza`, Slack `xox[baprs]-`, JWTs), and an inline `VARNAME=value` assignment where the name ends in `TOKEN`/`SECRET`/`KEY`/`PASSWORD`/`PASS`/`CREDENTIAL`(S), case-insensitive. Deliberately over-inclusive on that last pattern (a non-secret like `MONKEY=banana` also gets redacted, since it ends in `KEY`) - the right asymmetry for a security log, where losing a little detail is a much smaller cost than missing a real secret.
- **Explicitly scoped, not a claim of completeness**: this is pattern-based detection of common, structurally-recognizable secret shapes, the same class of technique git-secrets/gitleaks/truffleHog use, not an exhaustive filter. A bare, unlabeled random string with no recognizable prefix is not caught. `SECURITY.md`'s "Known gaps" list says this plainly, and the audit log should still be treated as potentially sensitive.

10 new regression tests (`test_redact.py` for the pattern-level behavior, plus wiring tests in `test_audit.py`), 406 tests passing (up from 395), 100% coverage on the new `redact.py` module. Re-verified end to end through the real hook path with the exact reported reproduction (a live-shaped bearer token on a `curl -H` flag): the token no longer appears anywhere in the written log entry.

## Reporting a vulnerability

If you find a way to make ccvet auto-approve something it clearly should not (a bypass of Layer 0's hard-coded guards in particular), please open an issue describing the command and the expected versus actual decision. If the bypass is severe enough that public disclosure before a fix would be actively harmful, say so in the issue and we'll coordinate privately first.
