# ccvet Implementation Plan

Risk-classifying `PreToolUse` gate for Claude Code. Public repo on https://github.com/saicharansreedhara2 (not mortalapps), published to PyPI as `pip3 install ccvet`. Layer 0/1 (rules + heuristics) must fully work with zero model configured; Layer 2 (LLM) is opt-in for the gray zone only. See `risk-taxonomy.md` for the full command classification that backs Phase 1.

## Phase 5: Testing and hardening, DONE 2026-11-24

### Critical finding: compound shell constructs bypassed classification entirely
While adding edge-case tests, found that **`{ rm -rf /; }`, `(rm -rf /)`, `if true; then rm -rf /; fi`, `while`, and `for` loops all evaluated to `allow`** instead of being classified at all. Root cause: bashlex represents brace groups, subshells, and the wrapper around if/while/for/until as a `CompoundNode` exposing its children through a `.list` attribute. Every other node kind uses `.parts`, which is the only attribute `shell.py`'s extraction walker checked. The compound wrapper's children were silently never visited, `extract_simple_commands()` returned an empty list, and `shellrules.evaluate()`'s "no commands found" fallback is `allow("empty command")`. That turned "nothing to classify" into "nothing dangerous found" for an entire class of shell syntax. This was a real classification bypass, not a cosmetic gap, and a determined adversary (or just an agent wrapping a command in `{ ...; }` for unrelated reasons) could have walked straight through Layer 0's hard-coded guards.

Fixed in `shell.py` (`_children()` now checks both `.parts` and `.list`). Verified against all five constructs plus confirmed a benign brace group (`{ ls -la; }`) still correctly allows. Permanent regression tests added at both the extraction level (`test_shell.py`) and the full end-to-end taxonomy table (`test_bash_rules.py`'s `BLOCK_CASES`), so this can't silently regress. `case` statements remain unparseable by bashlex entirely (a bashlex limitation, not fixable here) and fall to `ask`, not `allow`. Safe, just not actively classified; documented as a known gap rather than silently missing.

**This is exactly the kind of bug a hardening pass exists to find.** Worth flagging to the user prominently, not just logging in this file.

### Second round: a deliberate adversarial pass found three more of the same bug shape
Before deciding the repo was ready to make public, ran a short adversarial pass specifically looking for siblings of the compound-construct bug above (anything else that might not get walked into and visited). Found three more real gaps in the same session:
- **Process substitution** (`cat <(rm -rf /)`): structured like command substitution (a `.command` attribute), but under a different node kind (`processsubstitution`) that the existing special-case check didn't cover. `cat <(rm -rf /)` extracted to just `cat`, allowing straight through. Fixed by adding `processsubstitution` to the same branch as `commandsubstitution` in `shell.py`.
- **`eval`/`exec`/`command`/`builtin`** (`eval "rm -rf /"`, `exec rm -rf /`): these transparently run their argument as the real command, but ccvet was classifying the wrapper program name itself (`eval`, `exec`, ...), which isn't on any list, so it fell to a generic "unrecognized command" ask instead of being denied. Fixed in `rules.py`: `exec`/`command`/`builtin` recursively reclassify their remaining argv directly (bashlex already split it); `eval` re-parses its joined string argument through the real shell parser first, since that's what `eval` itself does at runtime.
- **ANSI-C quoting** (`rm $'-rf' /`): bashlex mis-parses `$'-rf'` as a parameter expansion rather than dequoting it to the literal `-rf`, so the catastrophic-rm flag check doesn't recognize it. This downgrades the result from `deny` to `ask`, not to `allow`, so it's a real gap but not a silent bypass. Documented as a known limitation in `SECURITY.md` and `risk-taxonomy.md` rather than patched, since a narrow fix here risks false confidence given bashlex's own ANSI-C quoting support is the actual weak point. `select`, `coproc`, `[[ ... ]]`, and arithmetic `for ((...))` were also checked and confirmed to fail safely (parse error, falls to `ask`), joining `case` as documented unparseable constructs.

All three fixes have permanent regression tests (`test_shell.py`, `test_bash_rules.py`); 227 tests passing, 99% coverage maintained. This round came from deliberately trying to break the same code path again rather than from routine coverage work, which is worth remembering as a technique: once you find one bug in a parser's node-kind coverage, go looking for its siblings before calling the area done.

## Deep review pass (2026-11-25): a full manual audit of every module, before deciding the repo was ready to push

Separate from the targeted adversarial pass earlier (which specifically hunted for siblings of one known bug shape), this was a line-by-line read of every module in `src/ccvet/` looking for anything wrong: logic bugs, missed cases, crash risks, usability gaps. Found and fixed 16 real issues, tracked here in severity order.

**High severity (real classification gaps):**
- Shell redirections (`>`, `>>`, `<`, `<<<`) were completely invisible to classification, since a redirect target never appears in a command's argument list. `curl ... < ~/.aws/credentials` (credential exfiltration via input redirect) and `echo ... >> ~/.bashrc`/`>> ~/.ssh/authorized_keys`/`>> /etc/crontab` (persistence writes) all evaded the secret/persistence guards entirely. Fixed: `shell.py` now extracts every redirect target (`extract_redirect_targets()`, reusing the same compound/substitution-aware tree walk as command extraction) and `rules.redirect_target_guard()` checks them against the same secret/persistence patterns Edit/Write tool paths already use.
- `paths.py`'s secret/persistence/manifest matching used a raw substring search on the full resolved path string: `/etc/passwd` matched `/etc/passwd_notes.md`, `.bashrc` matched `my.bashrc_backup.txt`, `package.json` matched `mypackage.json`. Since the secret-path match is a hard, non-overridable deny, a false positive there couldn't even be worked around by the user. Fixed: matching is now component-aware against the path's actual segments (`matches_any`/`path_text_matches_any`), with a pattern component ending in `_` still matching as a prefix (so `.ssh/id_` keeps catching `id_rsa`, `id_ed25519`, etc.).
- `CATASTROPHIC_RM_TARGETS`/`CATASTROPHIC_CHMOD_TARGETS` were missing `/var`, `/opt`, `/Applications`, `/Library`, `/root`, `/sbin`, `/boot`, `/private`, a bare `*`/`.*` wildcard, and any home-directory-root pattern (`/Users/<name>`, `/home/<name>`) wasn't recognized as catastrophic at all despite being just as destructive as `rm -rf /` for that user. Fixed: expanded the target lists and added `_looks_like_home_directory_root()`.
- `chmod`'s catastrophic check only recognized octal `777`/`000`, so `chmod -R a+rwx /` (symbolic mode, same effect) wasn't caught. Fixed: `_is_full_permission_grant()` also recognizes symbolic grants (`[ugoa]*[+=]rwx` in any permission-letter order).
- `find`'s guard only checked exact `-exec`/`-delete`, missing `-execdir`/`-ok`/`-okdir`, which are equally capable of running arbitrary commands on matched files. Fixed: all five flags checked.
- `sql_guard.py`'s DELETE/UPDATE-without-WHERE check scanned the whole command's text, so `psql -c "DELETE FROM users" -c "... WHERE ..."` (a genuinely unconditional delete, paired with an unrelated WHERE in a different `-c` argument) escaped detection. Fixed: the WHERE check is now scoped to the specific statement, up to the next `;` or closing quote.

**Medium severity (real bugs, generally caught by an outer safety net but degrading correctness):**
- `userpolicy.find_override()` resolved a rule's `verdict:` field via `getattr(Verdict, verdict_name, None)` with no whitelist. A hand-edited `verdict: defer` could be invoked (not something a user rule should produce), and `verdict: rank` (a real but unrelated `Verdict` method) would raise, discarding the already-computed correct built-in verdict for a generic internal-error `ask`. Fixed: an explicit `{"allow": ..., "ask": ..., "deny": ...}` whitelist.
- `userpolicy._load_file()` and `config._load()` didn't catch YAML parse errors. A malformed user `policy.yaml` or `config.yaml` would raise past the already-computed correct built-in verdict, degrading every single overridable Bash command to a generic internal-error `ask` until the file was fixed. Fixed: both now catch `yaml.YAMLError` (and reject a non-dict top level) and degrade to "nothing configured" instead.
- `classifier.classify()`'s exception handling was a curated list that missed `IndexError` (an empty `choices` array from a misbehaving server) and `TypeError` (a non-numeric `classifier.timeout_seconds`, since `ccvet config set` always stores CLI values as strings). Fixed: broadened to a blanket `except Exception`, matching the function's own stated "always fail to None" contract, and added explicit `float()` coercion with a safe fallback for the timeout.
- `classifier.py` embedded the raw command inside a markdown code fence in the Layer 2 prompt; a command containing a literal triple-backtick sequence could structurally break out of that framing. Fixed: the command is now JSON-encoded as a single string value instead, which neutralizes backticks/newlines/quotes.
- `init._load()` had no handling for malformed `.claude/settings.json`, crashing `ccvet init`/`ccvet uninstall`/`ccvet status` with a raw traceback. Fixed: raises a clear `ValueError` that all three call sites now catch and report cleanly.
- `config.set()`'s use of `setdefault` would raise `TypeError` if an intermediate key already held a non-dict value (e.g. a prior `classifier: some_string` entry). Fixed: explicitly overwrites a non-dict intermediate with `{}` instead of crashing on it.
- `commands.log_view()` used direct key access (`entry["ts"]`, etc.) with no fallback, so one valid-JSON-but-wrong-shape log line crashed the whole `ccvet log` command, not just that line. Fixed: wrapped per-entry, skipping only the bad line.

## Follow-up to the third round (2026-11-27): two observations on the fixes themselves, both addressed before a new release

Two more observations came in right after v0.0.5, this time about the fixes just shipped rather than new bypasses:

- **A bare variable redirect target (`cmd > $OUT`) was still a hard, non-overridable deny.** The ask-vs-deny downgrade above only widened the "pure, nothing concatenated" check to self-contained substitutions, not to a bare variable - so `OUT=report.txt; cmd > $OUT`, an entirely ordinary shell idiom with the same risk profile as `$(mktemp)`, still hard-denied with no escape hatch. Decided explicitly: no, keep Layer 2 restricted to the `ask` tier only, matching its own long-standing documented contract ("can only turn an ask into an allow, never a deny"), which held before only as an accident of the bug it was fixed alongside. `shellrules.evaluate()` now gates the classifier call on `verdict.decision == "ask"` in addition to `verdict.overridable`; the user-policy override above it is unaffected and still works on any overridable verdict, deny included, since that's an explicit human-reviewed rule, a different trust tier entirely from a one-shot local-model opinion.

Going forward: patch bump for a pure bug fix, minor bump for anything that changes observable behavior (the v0.0.9 round's redirect-target ask-vs-deny tradeoff is the kind of thing that would have warranted a minor bump under this rule, in hindsight).

## Verification of v0.0.10 (2026-11-27): a crash in the new warning itself, and a wording nit

A checksum-verified re-check of v0.0.10 confirmed it changed only `status()` (classification and `ccvet allow` behavior byte-identical to the already-verified v0.0.9), and that the new unanchored-rule warning behaves as documented. It also found two real issues in that same new code:

- **`ccvet status` crashed on a hand-edited `policy.yaml` with a non-mapping rule item** (`rules:\n  - just a string\n`), an `AttributeError` from calling `.get("match")` on a plain string. Confirmed directly, and confirmed the gate path was never affected: `userpolicy.find_override()` already guards exactly this case (`if not isinstance(rule, dict): continue`), specifically so a malformed policy file can't take anything down - the new `status()` loop was the one place that guard hadn't been carried over to. Fixed by mirroring it. Never a protection gap, just a crash in the one command whose job is telling you your policy is shaped wrong.
- **The warning's wording overstated reach for a partially-anchored rule.** `^docker build\.` (this project's own docstring example) is anchored at the start, a prefix match, not an unanchored "substring search anywhere" the way a fully unanchored pattern is. Fixed: each flagged rule now gets its own accurate description (prefix search, suffix search, or substring search anywhere) instead of one blanket claim covering all three shapes.

4 new regression tests in `test_commands.py` (the crash reproduction, prefix-wording, suffix-wording, and an empty-`match`-key edge case for full coverage). 386 tests passing (up from 382), 100% coverage on `commands.py` maintained.

**Released as v0.1.0 (2026-11-27)**: the versioning-correction release above, bumped `pyproject.toml`, verified the wheel locally in a clean venv before tagging (including a live crash-reproduction smoke test on the real built wheel), then tagged and pushed.

## Verification of v0.1.0 (2026-11-27): the status crash's real bug was one level down, and it was serious

A checksum-verified re-check of v0.1.0 found that the `isinstance(rule, dict)` guard added for the v0.0.10 crash stopped one level too early, and that the deeper version of the same gap was the most severe finding across ten review rounds so far - not a classification bypass, but something that could silently degrade ccvet's actual day-to-day value:

- **A non-string `match` value (`match: 5`, `match: true`, `match: [a, b]`) still crashed `ccvet status`** - the same shape of bug, one level down (the rule item was a dict, but its `match` value wasn't a string, and `match = rule.get("match") or ""` only filters a *falsy* value). That alone would have been another instance of the same crash class. The real severity: `userpolicy.find_override()` has the identical gap, and `find_override()` isn't a diagnostic command - it runs from `shellrules.evaluate()` on **every single overridable verdict**, which includes every plain `AUTO_PROGRAMS` auto-allow (`ls`, `cat`, `grep`, `git status`, ...), not just the hard-coded safety-floor guards. Confirmed directly: a single `match: 5` rule anywhere in `policy.yaml` raised an uncaught `TypeError` from `re.search(5, command)` inside `find_override()`, caught by `gate.py`'s blanket exception handler and silently turned into `ask` for every overridable command, project-wide, with a generic "internal error" reason giving no hint a malformed policy rule was the cause. Fixed in both places with the same guard: `isinstance(pattern, str)` before doing anything with it, skipping (not crashing on, not raising past) anything else - the same tolerance `_load_file`'s non-dict-rule handling already had.
- **Added, per the review's own suggestion**: `ccvet status` now counts and reports rules it couldn't evaluate (missing, empty, or non-string `match`) as an explicit "N rule(s) could not be evaluated" note, instead of silently skipping them with no visible trace - exactly the diagnostic gap behind the finding above.

9 new regression tests across `test_userpolicy.py` and `test_commands.py` (395 total, up from 386), 100% coverage on `commands.py` and `userpolicy.py` maintained. Re-verified end to end through the real hook path: `ccvet gate` with a seeded `match: 5` rule now correctly allows `ls -la` instead of degrading it to a generic `ask`.

This is a pure bug fix (the fixed behavior is "stop raising/crashing on a malformed rule", not a change to any classification decision), so per the versioning correction above it's a **patch** release, not minor.

**Released as v0.1.1 (2026-11-27)**: bumped `pyproject.toml`, verified the wheel locally in a clean venv before tagging, including a live reproduction of the degradation bug on the real built wheel (`ccvet gate` with a seeded `match: 5` rule, confirmed `ls -la` allows correctly), then tagged and pushed.

## Audit-log secret redaction (2026-11-27): closing the one item left open across four review rounds

The plaintext-audit-log finding had been raised four times (first in the "Adversarial and robustness testing round" above, confirmed real with an actual bearer token write) with the same conclusion each time: documented tradeoff, not a bug, no code change. Decided it was worth actually closing after the fourth flag rather than deferring again - user explicitly asked to "solve 1 clearly and reliably."

Design choice made up front: don't hash the whole command the way Write/Edit content already is. The audit log's entire stated purpose (`audit.py`'s own docstring) is "what command actually ran" for a human reviewing it later; hashing that away would defeat the log's purpose, not protect it. The right scope is targeted redaction of secret-*shaped* substrings within the command text, the same class of technique git-secrets/gitleaks/truffleHog use, not a blanket content hash.

Added `src/ccvet/redact.py`: pattern-based, applied to a Bash command's text and a `WebFetch` URL (the other raw-text field that can carry embedded credentials) before either is written. Patterns: `Authorization: Bearer`/`Basic` headers, URL-embedded credentials (`https://user:pass@host`), well-known provider token prefixes (OpenAI `sk-`, GitHub `gh[pousr]_`, AWS `AKIA`, Google `AIza`, Slack `xox[baprs]-`, JWTs), and an inline `VARNAME=value` assignment where the name ends in `TOKEN`/`SECRET`/`KEY`/`PASSWORD`/`PASS`/`CREDENTIAL`(S), case-insensitive. The last pattern is deliberately over-inclusive (`MONKEY=banana` also gets redacted, since it ends in `KEY`) - documented explicitly as the right asymmetry for a security log, favoring a little lost detail over a missed real secret.

Explicitly scoped and documented as best-effort, not exhaustive, in `SECURITY.md`'s "Known gaps": a bare, unlabeled secret with no recognizable structural shape at all won't be caught, and the audit log should still be treated as potentially sensitive.

10 new regression tests (`test_redact.py` plus `test_audit.py` wiring tests), 406 tests passing (up from 395), 100% coverage on `redact.py`. Re-verified end to end through the real hook path with the exact originally-reported reproduction (a live-shaped bearer token on a `curl -H` flag): the token no longer appears anywhere in the written log entry.

**Released as v0.2.0 (2026-11-27)**: bumped `pyproject.toml`, verified the wheel locally in a clean venv before tagging, including a live reproduction of the original leak on the real built wheel, then tagged and pushed.

## Verification of v0.2.0 (2026-11-27): a field the redaction fix never covered, and three regex gaps

A checksum-verified re-check confirmed every `redact.py` pattern behaves exactly as documented, then found the fix had a real hole: `redact.redact()` was applied to the `command`/`url` input fields but never to `verdict.reason`, which `audit.log()` writes raw. Serious because of how a `reason` string is actually built: `rules.py`'s `ASK_PROGRAMS` path interpolates the same raw argv text straight back in (`f"{program} {' '.join(args)}"`), and `ASK_PROGRAMS` includes `curl`/`aws`/`docker`/`kubectl`/`gcloud` - precisely the tools that carry credentials as CLI arguments. Confirmed with the sharpest case possible: an AWS access key that `command` correctly redacted survived verbatim in `reason` on the very same log line. Fixed with the one-line change suggested: `redact.redact(verdict.reason)` in `audit.log()`.

Three regex gaps in `redact.py` itself, all confirmed before fixing:

- **A bare keyword-only name never matched** (`password=`/`secret=`/`token=`/`key=`, arguably the single most common real-world form) - the name pattern required at least one character before the keyword suffix, so only a *prefixed* name like `API_PASSWORD=` matched. Fixed by making the leading identifier segment optional.
- **`curl -u`/`--user USER:PASS` basic auth wasn't covered** - the URL pattern only handled credentials embedded in a URL, not the same shape behind a flag instead. Added a dedicated pattern with the same treatment: username visible, password redacted.
- **A hyphenated, header-style name missed too** (`x-access-token=abc123`) - widened the character class to allow a hyphen, confirmed this introduces no new false positive since the name still has to *end* in a literal keyword (`--max-key-size=100` stays unredacted; "size" isn't one of the keywords).

4 new regression tests covering all four fixes plus the negative cases that must stay untouched (`PASSWORD_FILE=`, `--max-key-size=`, `ssh-keygen --public-key-path=`, `sort -u` with no colon). 413 tests passing (up from 406), 100% coverage on `redact.py` and `audit.py` maintained. Re-verified end to end through the real hook path with a command combining both new patterns at once.

This is a security bug fix (closing a real leak in the just-added redaction), not new classification behavior, so it's a **patch** release per the versioning rule.

**Released as v0.2.1 (2026-11-27)**: bumped `pyproject.toml`, verified the wheel locally in a clean venv before tagging, including a live reproduction of the `reason`-field leak on the real built wheel, then tagged and pushed.

## Verification of v0.2.1 (2026-11-27): a password containing its own colon

curl/URLs don't forbid a colon inside the password itself, and both the URL and `-u`/`--user` patterns assumed otherwise:

- **The URL case was the worse one**: a password containing a colon meant the password character class could never reach the required trailing `@`, so the whole credential was left completely unredacted, not just partially - `https://alice:pa:ss@github.com/x` passed through untouched. Fixed by allowing a colon in the password portion of `_URL_CREDENTIALS_RE` (the username portion still correctly stops at the *first* colon only, matching URL convention itself).
- **The `-u`/`--user` case degraded more gracefully but still leaked a tail**: `-u alice:pa:ssword` redacted only up to the second colon, leaving `:ssword` exposed. Fixed the same way - the password group now captures everything after the first colon up to whitespace, colons included.
- **`--cache-bypass=true` getting redacted isn't a new issue**, it's the already-documented over-inclusive-by-design tradeoff (`MONKEY=banana` in the module's own docstring is the same shape, "bypass" ends in "pass"), just flagged alongside the two real fixes above rather than something new to fix.

2 new regression tests for the colon-in-password case in both shapes. 415 tests passing (up from 413), 100% coverage on `redact.py` maintained.

**Released as v0.2.2 (2026-11-27)**: bumped `pyproject.toml`, verified the wheel locally in a clean venv before tagging, including a live reproduction of both colon-in-password shapes on the real built wheel, then tagged and pushed.

## Verification of v0.2.2 (2026-11-27): the colon-widening fix had its own regression

Allowing `:` in the URL password class (v0.2.2's own fix) had a side effect: it also let the password class sweep up a port-plus-query-string shape with an `@` in a query value *before any path slash*, e.g. `https://api.host:8443?email=a@b.com` misread as credentials with `8443?email=a` as the password. Confirmed exactly, including the two negative cases that already avoided it (a path slash before the `?`, or no `@` at all). Correctly characterized as log-noise only (over-redaction, the already-accepted-safe direction), not a security regression, but fixed precisely rather than left as a known quirk: an unencoded `?` unambiguously starts a query string in real URL syntax and could never legitimately appear inside a username or password, so excluding it from both character classes (alongside `/`) closes the gap exactly, not heuristically.

1 new regression test covering all three reported shapes. 416 tests passing (up from 415), 100% coverage on `redact.py` maintained.
